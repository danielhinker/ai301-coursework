# Rubric: is this reproduction package ready to post?

The package is the candidate claim comment plus the candidate repro report, read
against the Issue (title, body, and Thread highlights) and the Repo facts block. In
eval mode the bundle is the whole world. In live mode, the drafts are the candidate
side and the issue thread and repo docs are the issue side.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| behavior-matches-issue | The output, log, exit code, or screenshot shown in the Candidate repro report, and the input or command that produced it, read against the error or symptom and the trigger described in the Issue section (body plus maintainer notes in Thread highlights). | Pass if the shown output displays the same failure the issue describes (same error or exception, same kind of failure: a crash or panic is not a clean validation error, a hang is not a wrong result), produced by the issue's trigger. An equivalent command is fine (a file instead of a pipe), but the input that triggers the bug must be the issue's, not a changed one. Also pass if the report says it could NOT reproduce and shows the output it actually got from a real attempt at the issue's trigger. Fail if no output is shown, if the input or trigger was changed, or if the output shows a different failure (or a working program) while the report says it reproduced the issue. | required |
| environment-recorded | The environment record in the Candidate repro report (tool or library version, OS or platform, and anything else the issue says matters, such as a driver, shell, or build profile), read against the version and platform named in the Issue section and Repo facts. | Pass if the report names the version it tested and the OS it ran on, plus any setting the issue or a maintainer says changes the failure. Where the tested version or platform differs from the one the issue targets, the report must say so. Fail if the version or OS is missing, if a setting the issue says matters is missing, or if a different version or platform was used without saying so. | required |
| steps-rerunnable | The commands, input files, and configuration in the Candidate repro report, read together with the Issue (a report may reuse the issue's own snippet or input by reference). | Pass if a stranger with this report, the issue, and public software could get from a clean start to the trigger without guessing anything that matters to the failure. Commands are shown; an input may be pasted, or named as exactly the issue's input ("the issue's 12-line test.txt"), or described precisely enough to recreate (which keys, which values). Exact keypresses in an interactive tool count as shown. Fail if a step that matters to the trigger is too vague to recreate ("set up the project", "my usual config"), or if it depends on something private or unshared (a private repo, an internal config, an unshared file). | required |
| claims-backed | The outcome statements in the Candidate claim comment and Candidate repro report (that it reproduced or did not, what causes it, where else it happens), each read against the artifacts the report shows. | Pass if the report's central outcome (reproduced, or could not reproduce) is backed by a shown artifact, and any root cause or wider scope it states is either backed by an artifact or labelled as a guess or hypothesis. Supporting details (how many times it was re-run, a control described in words) do not need their own artifact. An evidenced cannot-reproduce that says what was tried and what differed passes. Fail if the report asserts a result, a root cause, or a wider scope as fact ("I verified the race", "guaranteed reproducible", "also broken on X") that no shown artifact supports. | required |
| claim-specific | The Candidate claim comment, read against the Issue. | Pass if the claim names something specific to this issue (the symptom, the trigger, or the component) and says what the author will do next (investigate, reproduce, report back), without promising a fix, a deadline, or a guaranteed outcome. Fail if it could be pasted onto any issue unchanged ("+1", "assign me", "I'd love to work on this"), or if it promises a fix or a date. | required |
| policy-respected | The `contribution policy` line in Repo facts (including any AI-use policy), read against both candidate comments. Live mode: CONTRIBUTING.md and any AI policy file. The bug-report template asks are for people opening issues, not for comments on an existing one, so they are not read here. | Pass if the comments meet what the stated policy requires of comments. When the policy requires disclosing AI assistance, at least one of the comments must say that AI tools were used and how; every package here is AI-assisted work. When the policy requires comments in the author's own words, the comments must not present themselves as AI output. Pass when the policy says nothing about AI or about comments. Fail if a required disclosure is missing, or a stated requirement for comments is broken. | required |
| control-run | The Candidate repro report. | Pass if the report includes a control: the same steps with the trigger removed or changed, showing the failure depends on it. | preferred |

## Verdict rule

Accept (ready to post) only if every `required` check passes. Any `required`
check that fails, or is `unclear`, means reject (hold): proof I cannot verify is
not ready to post. `preferred` checks never change the verdict. In live mode on a
claim-only draft, the checks that need the repro report are reported as not yet
applicable and left out of the verdict, as SKILL.md says; `claim-specific` and
`policy-respected` still decide it.
